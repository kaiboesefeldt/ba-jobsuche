# Agentischer Entwicklungsworkflow

Dieser Ablauf gilt, wenn der Nutzer Codex ein Issue dieses Repositorys zur Bearbeitung zuweist, etwa durch Nennung der Nummer oder des Links. Eine GitHub-Zuweisung allein startet keine Sitzung; ohne gesondert eingerichtete Ereignisverarbeitung ist ein Anstoß durch den Nutzer nötig. GitHub-Aktionen erfolgen über die eingerichtete GitHub-App; der Nutzer prüft und merged Pull Requests selbst.

1. Das aktuelle Issue über die API lesen und prüfen, dass es offen ist, das Label `approved` trägt und das Label `In progress` nicht trägt. Sind diese Voraussetzungen nicht erfüllt, nicht mit der Umsetzung beginnen; den festgestellten Zustand mitteilen. Die Labels nicht selbst als Ersatz für eine Freigabe vergeben.
2. Das Label `In progress` hinzufügen und das Issue dem Nutzer `kaiboesefeldt` zuweisen; anschließend beides über die API prüfen. Die Zuweisung bezeichnet den verantwortlichen Nutzer, während das Label die laufende Bearbeitung kennzeichnet. Kann das Label nicht gesetzt oder bestätigt werden, nicht mit der Umsetzung beginnen. Schlägt die Zuweisung fehl, dies mitteilen und ohne andere Zuweisung fortfahren. Bei einer bereits bestehenden Bearbeitung oder einem erkennbaren Konflikt nicht eigenständig übernehmen.
3. Die Umsetzung mit den anwendbaren Superpowers-Skills vorbereiten und ausführen. Entwurf und Implementierungsplan folgen den Skills und den Repository-Regeln. Die dort zerlegten Aufgaben werden nicht als GitHub-Sub-Issues angelegt.
4. Auf einem eigenen Branch arbeiten, Änderungen prüfen und einen Pull Request zur Prüfung erstellen. Das zugehörige Issue im PR nennen. Der Nutzer entscheidet über Freigabe und Merge; nicht eigenständig mergen.
5. Bei einer erneuten Beauftragung den aktuellen PR-Stand, Reviews, Kommentare und Prüfungen abrufen und relevante Rückmeldungen auf dem PR-Branch bearbeiten. Nach Änderungen erneut prüfen und den Stand mitteilen. Ein laufender Chat reagiert nicht selbstständig auf GitHub-Ereignisse; ohne gesondert eingerichtete Ereignisverarbeitung ist ein neuer Anstoß durch den Nutzer nötig.
6. Nach einem Anstoß den Merge-Status des zugehörigen PRs bei GitHub prüfen. Nur wenn der PR tatsächlich gemerged wurde, `In progress` vom Issue entfernen und das Issue schließen; anschließend den Zustand prüfen. Ein lediglich geschlossener oder noch offener PR zählt nicht als Merge. Ist das Issue bereits geschlossen, den Zustand prüfen und gegebenenfalls das verbliebene Label entfernen.

Für den Abschluss keine automatische Schließverknüpfung im PR voraussetzen: Sie kann ein Issue bereits beim Merge schließen, bevor der hier beschriebene Abschluss geprüft wurde. Fehlende Rechte, abweichende Zustände oder Fehler transparent melden und keine erfolgreichen Änderungen behaupten, die nicht bestätigt wurden.
